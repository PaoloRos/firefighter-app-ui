UI architecture

Feuerwehr Tools is a bilingual, local-first React interface for a growing collection of firefighter utilities. This page describes how the UI is composed, how data crosses its API boundary, and where a developer should extend it.

01 · Orientation

Architecture principles

Tool-oriented shell

The dashboard discovers utilities through cards; each tool owns a route, page state, API client, translations, and tests.

Same-origin boundary

UI code calls versioned relative /api/v1/ paths. Vite proxies them in development; FastAPI serves both sides in the production-like run.

Typed at the edge

TypeScript models define expected payloads, and the API client validates unknown JSON before page components consume it.

Bilingual and accessible

German is the default, Italian is persisted locally, and the shell supplies semantic navigation, focus handling, status announcements, and responsive controls.

02 · Composition

Functional map

The React shell owns navigation and shared context. Routes select a page; pages coordinate user interaction and delegate network work to a feature API client.

03 · Code ownership

UI modules

Application shell

  • Shared header, navigation, footer, and skip link
  • Route table and not-found view
  • Top-level i18n provider

Route pages

  • Dashboard composition
  • Tool-specific workflow and rendering state
  • Focus and announcement behavior

Reusable presentation

  • Typed props and semantic markup
  • No API or global-state ownership
  • Reusable dashboard-card pattern

Backend boundary

  • Endpoint and payload types
  • Runtime contract guards
  • Transport errors translated into safe states

Language boundary

  • German and Italian dictionaries
  • Stable API/issue-code translation
  • Persisted language preference

Visual system

  • Project-owned color, type, spacing, and shape tokens
  • 40 rem and 64 rem responsive transitions
  • Focus, reduced-motion, and 44 px target rules

04 · Interaction model

State and data flow

Tool workflow state is local to its page and represented as a discriminated union. This keeps impossible combinations out of the render path and makes every visible outcome explicit.

05 · Delivery

Runtime modes

Development · make dev

Browser :5173 Vite dev server and hot reload
↓ /api proxy
FastAPI :8000 loopback API server

Production-like · make run

Browser :8000 single local origin
↓ UI + /api
FastAPI :8000 serves Vite dist and versioned API

06 · Extension path

Adding another UI tool

  1. Add its metadata to the dashboard card collection.
  2. Create a page under src/pages/ and register its route.
  3. Keep request types and runtime validation in a feature API client.
  4. Add every visible string and stable error code to both dictionaries.
  5. Reuse design tokens and semantic patterns before adding new CSS.
  6. Cover the route, states, translations, API contract, and browser flow.

07 · Out-of-scope internals

Functionality boundary

Calendar conversion

The first tool accepts CSV/XLSX schedules and returns structured validation results plus in-memory ICS text. Parsing, event validation, and calendar generation belong to the separately versioned calendar-conversion framework; the UI depends only on the versioned web API contract.
